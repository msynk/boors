## 1. .NET 10 LTS and Blazor in 2026 (render modes, WASM, PWA, offline, SignalR); .NET 11 previews

### Takeaway
.NET 10 (GA 11 Nov 2025, LTS to Nov 2028) is the right baseline; Blazor in .NET 10 adds circuit-state persistence, declarative `[PersistentState]`, `ResourcePreloader`, inlined boot config, response streaming by default, PWA `updateViaCache:'none'`, and new JS-interop constructor/property APIs. .NET 11 (STS, GA expected 10 Nov 2026 per secondary sources) previews a CoreCLR-based WASM runtime with multithreading (stable only in .NET 12), Blazor WASM Aspire production hosting, and auth-token refresh for long-lived SignalR/Blazor Server connections. No SignalR-protocol changes landed in ASP.NET Core 10.

### Inferences
- For a personal-first app with heavy client-side compute (3,000-row grid diffs, chart updates), Blazor WebAssembly (standalone or Auto) is the natural web target; `[PersistentState]` and circuit persistence make Blazor Server viable too, but Server would route every 5-second diff through the circuit, so WASM + SignalR hub for market diffs is the cleaner split.
- Multithreaded WASM is a .NET 12 (2027) story; do not plan on Web Workers for CPU-bound indicator calculation in .NET 10. Push heavy maths to the server or to JS (chart libraries do their own rendering).
- Offline on the web is PWA/service-worker only; true offline-first (local DB, sync) is where MAUI Blazor Hybrid or the bit Boilerplate "offline database and sync" feature matters (see section 5).

### Gaps
- Could not find authoritative .NET 10 Blazor WASM download-size/startup benchmark numbers; the only figures found (Syncfusion, "114 MB vs 192 MB Brotli") look implausible and undocumented. The official learn.microsoft.com ASP.NET Core 11 release-notes page returned 404 at time of research, so .NET 11 Blazor details are from secondary summaries.
- Exact .NET 11 RC release dates not verified from devblogs.microsoft.com.

## 2. bit BlazorUI and bit Boilerplate (bitplatform.dev); alternatives (MudBlazor, Radzen, Syncfusion, Telerik, Fluent UI)

## 3. Charting for finance in Blazor (Lightweight Charts v5, Advanced Charts, ECharts, Plotly, SciChart, LightningChart, D3; Blazor wrappers; .NET-native charts)

### Takeaway
TradingView Lightweight Charts v5.2.1 (12 Aug 2026, Apache-2.0 with a mandatory TradingView attribution link, 35 KB) now has native multi-pane, price-positioned markers, context-aware tick formatters, and an official plugin package set (16 Sep 2026) — it is the free, licence-safe candlestick engine. TradingView Advanced Charts is "free with TradingView logo" but the Free Advanced Charts Agreement (v.0626.FAC, June 2026) restricts it to companies, public free-access implementations only, explicitly excludes "private, personal or internal uses", forbids open-source/public repos, requires marketing backlinks and gives TradingView free access to your product — **LICENCE BLOCKER for a personal-first app**. Apache ECharts 6.1.0 (19 May 2026, Apache-2.0) covers treemap/heatmap/calendar/matrix. Commercial options: SciChart.js $1,299–$1,699 per developer per year. Blazor wrappers: Blazor-ApexCharts 7.0.0 (MIT, Jul 2026); no official AG Grid or Lightweight Charts Blazor wrapper found.

### Inferences
- Lightweight Charts v5 via JS interop is the only choice that is free, licence-safe for personal-then-commercial use (Apache-2.0 + visible attribution link), and finance-native (candles, multi-pane, markers). Jalali axis labels are achievable through `tickMarkFormatter` + `timeFormatter` with a JS Jalali library (section 10) since the API gives full control over label text; however no RTL/mirrored time axis exists, so the chart will stay LTR inside an RTL page (which is normal for Persian finance UIs).
- Advanced Charts is unusable for this project as planned: the agreement excludes personal/internal use, requires a company licensee, requires public free access, forbids paywalls, and would prohibit publishing the app's source. Even a later commercial release behind a subscription would need Trading Platform / negotiated terms. **Remove it from the architecture.**
- ECharts (Apache-2.0) is the right companion for treemaps/heatmaps/calendars/market-map; its matrix coordinate system (6.0+) suits sector heatmaps. ApexCharts via Blazor-ApexCharts is a lighter alternative if a typed C# API is preferred, but it is not finance-specialised.

## 4. High-performance live grids in Blazor (Virtualize, BitDataGrid, QuickGrid, AG Grid, Telerik/Syncfusion) with ~5 s cell updates on 3,000 rows

### Takeaway
QuickGrid (in-box, MIT) and BitDataGrid both virtualise rows with fixed `ItemSize`/`Height` and support provider callbacks, and QuickGrid in .NET 10 adds `ScrollToItemAsync`, `InitialItemIndex`, experimental `AnchorMode`/`ItemComparer`; Microsoft explicitly says QuickGrid will not grow advanced commercial-grid features. No Blazor grid documents cell-level patching; the practical pattern from practitioners is to throttle/batch SignalR messages and avoid replacing the collection. AG Grid has only community Blazor wrappers (AgGrid.Blazor 0.9.0, small feature subset) and Enterprise needs a commercial licence.

### Cited Findings
- QuickGrid: "serves as a reference architecture and performance baseline"; `Virtualize` requires `ItemSize` and constant row height; `OverscanCount` default 3; new `InitialItemIndex`, `ScrollToItemAsync`, experimental `AnchorMode` and `ItemComparer` (opt-in via `ASP0030`); `ItemsProvider` must return accurate `totalItemCount`; `PlaceholderTemplate` for unloaded cells — [Microsoft Learn: QuickGrid](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/quickgrid) (page updated 2026-10-08)
- "There aren't current plans to extend QuickGrid with features that full-blown commercial grids tend to offer, for example, hierarchical rows, drag-to-reorder columns, or Excel-like range selections. If you require advanced features... continue using third-party grids." — [Microsoft Learn: QuickGrid](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/quickgrid)
- QuickGrid + EF Core concurrent queries throw `InvalidOperationException`; tracked in dotnet/aspnetcore #58716; workaround is `ItemsProvider` with cancellation token — [Microsoft Learn: QuickGrid](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/quickgrid)
- BitDataGrid: row and column virtualisation, `OnRead` server callback, `OnLoadMore`, resizable columns, RTL via `Dir="BitDir.Rtl"` — [bit BlazorUI docs: DataGrid](https://blazorui.bitplatform.dev/components/datagrid)
- Practitioner anecdote: Syncfusion Blazor WASM grid fed by SignalR lagged after ~100 rows without virtualisation; with virtualisation and no page size, scroll snapped to top on each arrival; with page size, later pages rendered blank — [Syncfusion forum 164186](https://www.syncfusion.com/forums/164186/grid-virtualization-strange-behavior)
- Real-time Blazor guidance: throttle high-frequency streams and batch UI updates so the browser isn't overwhelmed with redraws — [Tim Purdum, Sessionize](https://sessionize.com/s/TimPurdum/real-time-data-visualization-in-blazor/174892)
- Vendor benchmarks: Syncfusion vs Telerik 1M-record virtualised comparison; Infragistics live-data demo replaces grid data on a timer — [Syncfusion comparison](https://www.syncfusion.com/explore/?p=21459); [Infragistics](https://www.infragistics.com/products/ignite-ui-Blazor/Blazor/components/grids/grid/live-data) (both vendor-run)
- AG Grid Blazor: `AgGrid.Blazor` 0.9.0 is a community project exposing "a relatively small subset" of AG Grid features; `MeshWeaver.Blazor.AgGrid` warns it uses AG Grid Enterprise which "requires a commercial license for production use" — [NuGet: AgGrid.Blazor](https://www.nuget.org/packages/AgGrid.Blazor); [NuGet: MeshWeaver.Blazor.AgGrid](https://www-0.nuget.org/packages/MeshWeaver.Blazor.AgGrid/2.0.0-Preview2); [GitHub: glazkovalex/blazor-ag-grid](https://github.com/glazkovalex/blazor-ag-grid)

### Inferences
- 3,000 rows × refresh every 5 s is modest if the grid is virtualised (only ~30–60 DOM rows exist) and updates mutate existing row objects in place and call `StateHasChanged` once per batch; the cost is dominated by diffing the visible rows, not by 3,000 items. Both QuickGrid and BitDataGrid satisfy this; BitDataGrid adds RTL and column virtualisation out of the box, so it is the natural pick alongside bit BlazorUI.
- Cell-level flash animations (price up/down) should be done with CSS classes keyed on a change timestamp in the row model, not per-cell components, to keep render-tree diffs cheap.
- If a sophisticated grid (Excel-like ranges, pivoting) becomes necessary later, AG Grid via raw JS interop (Community edition is MIT) is viable but the Blazor wrappers are immature; Syncfusion under Community Licence is the lowest-friction commercial-grade grid while eligibility lasts.

### Gaps
- No independent benchmark of any Blazor grid at the "3,000 rows, cell updates every 5 s" profile exists in the sources; this needs an in-project spike.
- Telerik/Syncfusion grid-specific live-update APIs (e.g. observable-collection support) were not researched in detail.

## 9. Telegram.Bot; .NET clients for Bale bot API (Telegram-compatible?); Eitaa bot API

### Takeaway
Telegram.Bot 22.10.3.3 (9 Oct 2026, MIT, Bot API 10.3) is current. Bale's official docs state its Bot API is "based on the Telegram Bot API" with the same method names (`getUpdates`, `sendMessage`, webhooks on ports 443/88, payments via `sendInvoice`), served at `https://tapi.bale.ai/bot<token>/`, so Telegram.Bot can be pointed at it; dedicated .NET packages exist (BaleBotNet 5.0.0, BaleSharp 2.1.1, HexaBale 1.3.0). Eitaa has only the third-party "Eitaayar" send-message API (token from eitaayar.ir) with Python/PHP wrappers — no .NET package and no official full bot API found.

### Cited Findings
- Telegram.Bot 22.10.3.3 (9 Oct 2026), MIT, Bot API 10.3, .NET Standard 2.0 / .NET 6+, 10.6M downloads — [NuGet: Telegram.Bot](https://www.nuget.org/packages/Telegram.Bot); Bot API 10.2 was released 14 Jul 2026 — [NuGet: Telegram.Bot 22.10.2-dev.3](https://www.nuget.org/packages/Telegram.Bot/22.10.2-dev.3); alternative Telegram.BotAPI 10.2.0 — [NuGet: Telegram.BotAPI](https://www.nuget.org/packages/Telegram.BotAPI/)
- Bale Bot API: base `https://tapi.bale.ai/bot<token>/METHOD_NAME`, files at `/file/bot<token>/<file_path>`; "based on the Telegram bot API" with minor changes so Telegram bot libraries can generally be used; Bale-specific methods `askReview` and `inquireTransaction` need raw HTTP; long polling or webhook (`setWebhook`, ports 443 and 88; last 2,000 updates kept 24 h); payments via Bale e-wallet `sendInvoice`/`createInvoiceLink`/`answerPreCheckoutQuery` (10-second pre-checkout response), card-to-card no longer supported; Business API subset at `/business/bot<TOKEN>/` — [Bale docs](https://docs.bale.ai/)
- .NET Bale packages: HexaBale 1.3.0 (strongly typed, keyboards, payments) — [NuGet: HexaBale](https://www.nuget.org/packages/hexabale); BaleBotNet 5.0.0 (ASP.NET Core webhooks) — [NuGet: BaleBotNet 5.0.0](https://www.nuget.org/packages/BaleBotNet/5.0.0); BaleSharp 2.1.1 (.NET 8+) — [NuGet: BaleSharp](https://www.nuget.org/packages/BaleSharp)
- Eitaa: tokens from "https://eitaayar.ir/"; Python wrappers (pyeitaa, eitaapy, eitaa-pykit) expose send-message with chat id, text, optional pin/title/silent/view-count auto-delete; must add `@sender` as manager of the channel; PHP packages for Eitaayar API — [PyPI: pyeitaa](https://pypi.org/project/pyeitaa/); [PyPI: eitaapy](https://pypi.org/project/eitaapy/); [PyPI: eitaa](https://pypi.org/project/eitaa/); [Packagist: usermp/eitaayar](https://root.packagist.org/packages/usermp/eitaayar)

### Inferences
- A single notification abstraction can target Telegram and Bale with the same Telegram.Bot client by overriding the base URL (Telegram.Bot supports custom API servers), falling back to raw `HttpClient` for Bale-only methods. Verify Bale's `parse_mode`/markup differences in a spike.
- Eitaa integration is send-only via Eitaayar and needs a small `HttpClient` wrapper; do not plan interactive bot features for Eitaa.

### Gaps
- Licence, download counts and maintenance of the Bale .NET packages were not checked. Eitaayar's official API documentation page was not fetched; endpoint list and rate limits unknown.

## 10. Persian/Jalali in .NET and Blazor: PersianCalendar, Jalali libraries (C# and JS interop), Vazirmatn, Persian digits

### Takeaway
On the .NET side, DNTPersianUtils.Core 7.0.2 (26 Sep 2026, Apache-2.0) provides Jalali formatting, Persian digits, a corrected Persian culture and Iranian validators; bit BlazorUI's date picker renders the Persian calendar natively via `Culture`. On the JS side (needed for chart axes), Day.js Jalali plugins are low-activity (jalali-plugin-dayjs last updated Aug 2024; jalaliday upstream unmaintained per its fork). Vazirmatn v33.003 is OFL-1.1 with a variable font and RD/NL variants.

### Cited Findings
- DNTPersianUtils.Core 7.0.2 (26 Sep 2026), Apache-2.0, net5.0+ incl. net10.0, netstandard 1.3/2.0/2.1, .NET Framework 4.6+, 564.1K downloads; converts dates to Persian (Jalali) text/short/long formats and back, numbers to Persian words, Latin to Persian digits, provides a corrected Persian culture, Hijri conversion, Iranian national code/mobile/postal/Sheba/Shetab validation, text normalisation (Arabic ي/ك fixes), provinces, official holidays and business-day calculations — [NuGet: DNTPersianUtils.Core](https://www.nuget.org/packages/DNTPersianUtils.Core)

- Lightweight Charts exposes `tickMarkFormatter`, `timeFormatter`, `priceFormatter`, `tickmarksPriceFormatter` for custom axis/crosshair text — [LocalizationOptions](https://tradingview.github.io/lightweight-charts/docs/api/interfaces/LocalizationOptions); [TimeScaleOptions](https://tradingview.github.io/lightweight-charts/docs/api/interfaces/TimeScaleOptions)

### Inferences
- Do Jalali conversion in C# (`System.Globalization.PersianCalendar` or DNTPersianUtils) and pass pre-formatted axis labels or a compact Jalali lookup to JS, or use the browser's built-in `Intl.DateTimeFormat('fa-IR-u-ca-persian')` — the Intl approach needs no npm dependency and sidesteps the stale Day.js Jalali plugins (the jalaliday README itself mentions an Intl-based module). Persian digits: use `Intl.NumberFormat('fa-IR')` in JS or DNTPersianUtils in C#; for charts prefer Latin digits on price axes for density unless users opt in.
- Vazirmatn's variable font and OFL licence make it safe to bundle in web, PWA and MAUI builds; its NL variant can reduce size when Latin falls back to a system font.
- Blazor WASM must include fa-IR ICU data (default `InvariantGlobalization=false`, full or sharded ICU) — budget the extra download.

### Gaps
- Could not confirm from primary sources whether bit BlazorUI's Persian calendar is implemented via `System.Globalization.PersianCalendar`; the `CultureInfoHelper.cs` reference suggests a customised culture.
- Vazirmatn's Google Fonts availability and last-commit date were not shown on the page fetched. No source evaluated `Intl` Persian-calendar support across WebView2/WKWebView/Android WebView for the MAUI client.
